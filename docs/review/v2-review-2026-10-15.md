## Findings

### 1. Low: `onFailure` still makes an unbounded call into the untrusted stream token

`src/Weir.sol:386` (NatSpec), `src/Weir.sol:783` (`_defer`)

The v2 NatSpec on `onFailure` and the README both say the failure callback "makes no call into the stream token". It does: `_defer` ends with `_assertSolvent(token)`, which calls `token.balanceOf(address(this))` with all remaining gas. A token whose `balanceOf` burns gas therefore still defeats the Intake's 200,000 stipend, exactly as v1 finding 6 described for `transfer`.

**Reproduction.** ERC-20 whose `balanceOf` loops forever when armed; `createStream` on it, recipient `accept`, recipient `dispute` (bond 50e6); arm the token; `intake.failRequest(receipt, 2, "x", 0, 0)` (the mock forwards 200,000 gas). Observed: the callback returns `false`, `streams(id).state == Disputed`, bond still held. The bond is then locked until `expireDispute`, and on that token `expireDispute` costs a near-full block because `_pushOrDefer` also reads `balanceOf` with unbounded gas before its capped `transfer`.

**Impact.** Bounded: the stream token is chosen by the client and vetted by the recipient at `accept`, and a token that burns gas in `balanceOf` also blocks its own `withdraw`, `refund` and `deposit`. The defect is that the documented v2 property (failure callback cannot be blocked by the token) does not hold.

**Fix.** Remove `_assertSolvent(token);` from `_defer`. The check can never fail there: in `onFailure` the books move `bond` from `escrowed` to `unclaimed` with the balance untouched; in the refused branch of `_pushOrDefer` both balances have just been proven unchanged. Removing it also frees bytes. Add a regression: `QuirkyToken` with a `burnBalanceOf` flag, `onFailure` under 200,000 gas must deliver.

The remaining unbounded `balanceOf` reads in `expireDispute`, `enforce` and every withdrawal path are inherent to the balance-checked accounting and are covered by the README's "tokens that lie about balances ... can block settlement" disclosure. Confidence: high.

### 2. Low: a 32-byte non-bool return word from `transfer` reverts settlement instead of deferring

`src/Weir.sol:759`

```solidity
bool refused = !ok || (returndata.length != 0 && (returndata.length < 32 || !abi.decode(returndata, (bool))));
```

`abi.decode(returndata, (bool))` reverts with empty data when the word is anything other than 0 or 1. `enforce` and `expireDispute` then revert in full, so the stream stays Ruled or Disputed; the client cannot void and the counterparty's bond is unreachable. The README promises that settlement payouts "never block a state transition".

**Reproduction.** ERC-20 whose `transfer` returns the word `2`; stream on it, dispute, signed `true` ruling delivered through the Intake (`state == Ruled`); arm the token; `enforce(id)`. Observed: `enforce` reverts with empty revert data, `state` remains `Ruled`.

**Fix.** Decode as an integer, which never reverts:

```solidity
abi.decode(returndata, (uint256)) != 1
```

Re-probed with the fix: a token that moves the funds and returns garbage reverts with `TransferMismatch` (correct, it lied); a token that returns garbage without moving funds is deferred. Confidence: high.

### 3. Info: README names a `disputeEndedAt(id, party)` getter that does not exist

`README.md:132`, `src/Weir.sol:176`

The mapping is `internal`, so there is no getter; a front end can learn the cooldown end only by simulating `dispute` and reading `CooldownActive(until)` from the revert. Either make the mapping `public` (the size trims below leave room) or reword the README. `fundDay` and `fundDisputesToday` are also `internal`, so a UI cannot show how many subsidised disputes remain today; optional.

### 4. Info: dead guard in `enforce`

`src/Weir.sol:413`

```solidity
if (s.rate != 0) emit Restarted(id, s.rate);
```

`pausedRate` is never zero while a stream is Disputed or Ruled: a fresh stream has `rate > 0`; `_dispute` copies a positive rate into `pausedRate`; `pause()` sets it; `restart()` clears it only while setting `rate > 0`; `_close` zeroes both but only on the way to Closed. After `s.rate = s.pausedRate` the condition is always true. Removing it saves bytes.

### 5. Info: the daily subsidy allowance doubles across the UTC day boundary

`src/Weir.sol:562`

Five subsidised disputes at 23:59:59 and five more at 00:00:00 drain 4 IMD of the fund in one second (probe: `fund drained in 1s: 4e18`). This matches the stated rule (five per UTC day) and is the normal property of a fixed-window counter; the README's "at most about four times that per day" understates the burst. Document "up to 4 IMD across a day boundary", or accept.

### 6. Info: residual channels in the quoted question text

`src/Weir.sol:496`, `src/libraries/OracleText.sol:53`

`neutralize` replaces only the ASCII double quote, which is the only hard delimiter the template uses; the "evidence, not instructions" label is the real defence. Two residuals:

- `validate` accepts control bytes below 0x20 and `neutralize` leaves them, so a note can insert newlines and visually start a new paragraph inside the quotes. Option: map bytes below 0x20 to a space in `neutralize` (about 20 bytes of code) or reject them in `validate`.
- Curly and fullwidth quotes (U+201C, U+201D, U+FF02) are valid UTF-8 and pass untouched. Not worth code; document.

Checked and fine: `expectedBody` and the body `dispute` sends come from the same `questionFor` → `_body` path with identical inputs; only `block.number` differs between blocks, which the README already states. Backslashes survive JSON escaping as literal backslashes and cannot close a quote.

### 7. Info: the cooldown also applies after an oracle failure that is not the disputer's fault

`src/Weir.sol:342`, `src/Weir.sol:690`

A status 1 or 2 failure (body refused, panel did not reach quorum) starts the same 7-day cooldown as an expiry, so the disputer cannot retry and the counterparty has a 7-day window to void. This is a design choice that follows the audit's suggested fix; note it in the README. No bypass was found: the cooldown is keyed by stream and `msg.sender`, written on every exit that returns the stream to Active (expiry, failure, accepted ruling), and a rejected ruling closes the stream. Alternating parties requires the counterparty to raise disputes itself, so it cannot be used against that counterparty.

### 8. Info: `forge build --sizes` exits non-zero because of a test contract

`LaunchTokenDeploymentHarness` (a test harness) is 29,150 bytes. Not Weir; use `--skip test` in CI or ignore.

## Size

Findings 2 and 4 applied together on d43d9c2: **24,489 bytes (−51)**, all tests green (162 plus the five probes). Finding 1 removes a further internal call. Enough headroom to make `disputeEndedAt` public if wanted.

## Checked and found fine

- **Bond credit in `onFailure`.** `_takeBond` lowers `escrowed` by `bond`, `_defer` raises `unclaimed` by `bond`, balance untouched, so `escrowed + unclaimed (+ courtFund for IMD) <= balance` holds. `claim` lowers `unclaimed` before the push. Zero bond: `_defer` returns early, no event. Cold `onFailure` with a standard token measures about 99,000 gas in the callee frame at `optimizer_runs = 1`, under the 200,000 stipend; the existing `onOracleResult` stipend tests still pass at the new optimizer setting.
- **Cooldown ordering.** The check precedes the recipient's implicit `_accept`, so a refused dispute records no acceptance. `enforce` stamps the cooldown at enforcement time; `enforce` is permissionless so neither party can hold the other in Ruled.
- **Fee split.** `own = price * 2000 / 10000`; `own + (price − own) == price` exactly; `own == 0` only for `price < 5` wei, which the Intake would have to set. The disputer's share is pulled in the same transaction as `requestWithFailure`; an Intake revert, an under-pull (`TransferMismatch`) or a request-id collision (`InvalidRequestId`) reverts the whole dispute, so no path pulls the share and then fails to request. The daily counter increments only when the fund actually pays. `fundDay`/`fundDisputesToday` pack into one slot.
- **Bounded gas in `_pushOrDefer`.** A token that moves funds and returns false, or returns true without moving them, hits `TransferMismatch`, not a deferral. A token that runs out of its 300,000 gas has its state reverted, so nothing moved. A caller cannot force a deferral by calling `enforce` with tight gas: when the forwarded gas is small enough for an honest token to run out, the 1/64 remainder is not enough for the balance reads that follow (probed across 60,000–400,000 gas in 5,000 steps; no window). Return data is copied into the caller's memory but its size is bounded by what the callee can afford within 300,000 gas. A token re-entering during the capped call meets the reentrancy guards.
- **Acceptance.** `_withdraw` records acceptance only for `amount != 0 && state == Active`; a withdrawal during a dispute no longer records hindsight acceptance.
- **`submitAttestation` removal, any-status `onFailure`, `Paused`/`Restarted` events, `MAX_QUESTION_BYTES` removal.** Match the README's "Changes since v1" table.

## Assumptions

The Intake is trusted and forwards a 200,000 gas stipend to callbacks, as the README states. The stream token is untrusted but chosen by the client and vetted by the recipient; findings 1 and 2 are rated Low on that basis. No live-chain request was made.
